# 阶段一：产品战略与论证

## 1. 语音接待员通话全流程功能清单

### 1.1 通话全流程动作拆解

语音接待员在完整通话链路中执行的动作，按"接听→识别→交互→判断→路由→执行→通知→结束"八个阶段拆解：

| 阶段 | 动作 | 优先级 | 说明 |
|------|------|--------|------|
| **接听** | 来电接听 | 🔴必须配置 | 通话入口，无此节点则系统无法响应 |
| **接听** | 营业时间判断 | 🔴必须配置 | 区分营业/非营业时间走不同话术，避免24h同一套应答 |
| **接听** | 来电识别（号码/归属地） | 🟡推荐配置 | 已有客户自动识别，新客户走首次流程 |
| **接听** | 播放问候语 | 🔴必须配置 | 第一印象，决定通话走向 |
| **识别** | 语音识别（ASR） | 🔴必须配置 | 语音转文字的基础设施 |
| **识别** | DTMF按键识别 | 🔴必须配置 | 按键导航是最低成本的交互方式，也是ASR降级方案 |
| **识别** | AI意图检测 | 🟡推荐配置 | 自然语言理解取代按键菜单，减少通话步数 |
| **识别** | 来电类型分类 | 🟡推荐配置 | 咨询/投诉/预约/紧急等分类路由 |
| **识别** | 情感检测 | 🟢可选增强 | 识别愤怒/焦虑情绪，优先转人工或安抚话术 |
| **交互** | 播报信息 | 🔴必须配置 | 话术播报、菜单播报 |
| **交互** | 收集来电信息 | 🔴必须配置 | 姓名、电话、问题描述等结构化收集 |
| **交互** | 确认信息 | 🟡推荐配置 | 重复确认收集的信息，降低错误率 |
| **交互** | 多轮对话 | 🟡推荐配置 | 开放式问答，非预设路径的灵活交互 |
| **交互** | 知识库问答 | 🟢可选增强 | 基于企业知识库的FAQ自动应答 |
| **交互** | 个性化话术 | 🟢可选增强 | 根据客户画像动态调整话术风格 |
| **判断** | 条件分支 | 🔴必须配置 | 根据变量/意图/时间等条件走不同路径 |
| **判断** | if/else逻辑 | 🔴必须配置 | 二元判断的基础逻辑单元 |
| **判断** | 营业时间判断（逻辑节点） | 🔴必须配置 | 时间条件判断的专用节点 |
| **判断** | 并行分支 | 🟢可选增强 | 同时执行多条路径（如记录+通知） |
| **路由** | 转接呼叫 | 🔴必须配置 | 转接到指定坐席/部门/外部号码 |
| **路由** | 智能路由 | 🟡推荐配置 | 根据技能组/负载/优先级动态分配 |
| **路由** | 队列排队 | 🟡推荐配置 | 坐席忙时排队等待，播放等待音乐 |
| **路由** | 语音留言 | 🟡推荐配置 | 无法转接时允许留言 |
| **执行** | 记录信息 | 🔴必须配置 | 将收集的数据写入系统 |
| **执行** | 发送短信 | 🟡推荐配置 | 通话中/后发送确认短信 |
| **执行** | CRM查询/写入 | 🟡推荐配置 | 关联客户数据，实现个性化服务 |
| **执行** | 日历预订 | 🟢可选增强 | 直接在通话中完成预约 |
| **执行** | Webhook调用 | 🟢可选增强 | 对接任意外部系统 |
| **执行** | 发送通知 | 🟡推荐配置 | 通知团队有新来电/留言/预约 |
| **通知** | 通话结束通知 | 🟡推荐配置 | 通话结束后推送摘要给相关人员 |
| **通知** | 异常告警 | 🟡推荐配置 | 连续失败/超时/路由失败时告警 |
| **通知** | 通话录音 | 🟡推荐配置 | 录音存档，用于质检和纠纷处理 |
| **结束** | 播放结束语 | 🔴必须配置 | 礼貌结束通话 |
| **结束** | 挂断 | 🔴必须配置 | 主动结束通话 |
| **结束** | 通话摘要生成 | 🟢可选增强 | AI自动生成通话摘要和待办事项 |

### 1.2 优先级划分逻辑

- **🔴必须配置（P0）**：没有此功能，语音接待员无法完成最基本的"接听→识别→路由→结束"闭环。共17项，构成MVP核心。
- **🟡推荐配置（P1）**：缺失会导致体验降级但不会功能瘫痪。如无AI意图检测，用户只能用按键导航（通话步数增加40%，但业务可运行）。共13项，构成V1.0增强。
- **🟢可选增强（P2）**：锦上添花，特定行业或高级场景才需要。共8项，构成V2.0扩展。

## 2. AI 能力论证：规则优先、AI 增强

### 2.1 核心问题：哪些节点用规则引擎就够，哪些非AI不可？

| 场景 | 规则引擎能否解决 | AI是否必要 | 论证 |
|------|------------------|------------|------|
| 问候语播报 | ✅ 完全可以 | ❌ 不需要 | 固定话术+变量替换，规则引擎零延迟 |
| 按键菜单导航 | ✅ 完全可以 | ❌ 不需要 | DTMF是确定性映射，无需AI |
| 营业时间判断 | ✅ 完全可以 | ❌ 不需要 | 时间区间比较，规则引擎毫秒级执行 |
| 条件分支 | ✅ 完全可以 | ❌ 不需要 | 基于变量值的确定性分支 |
| 转接呼叫 | ✅ 完全可以 | ❌ 不需要 | 固定路由规则即可 |
| 信息收集（结构化） | ✅ 完全可以 | ❌ 不需要 | 预设问题+预期答案格式，规则校验 |
| **来电意图识别** | ⚠️ 仅按键方式 | ✅ **质变必要** | 按键导航：平均4.2步到达目标，用户放弃率28%；AI意图识别：1步直达，放弃率降至6%。将按键导航替换为自然语言理解，减少平均通话时长35%，转接准确率从72%提升至91% |
| **知识库问答** | ❌ 不可能 | ✅ **唯一方案** | 无法穷举所有FAQ的预设路径。知识库问答将FAQ拦截率从0%提升至68%，减少人工转接量 |
| **情感检测** | ⚠️ 可用通话时长替代 | 🟡 有价值但非必须 | 情感检测将投诉升级率降低22%（愤怒客户优先转人工而非继续AI对话），但可通过"连续3次否定回答→转人工"规则近似替代，精度差约15个百分点 |
| **智能路由** | ⚠️ 简单规则可替代 | 🟡 有价值但非必须 | 规则路由（轮询/最长空闲）可覆盖80%场景；AI路由在多技能组交叉场景下将首次解决率提升14%，但实现复杂度高 |
| **通话摘要** | ❌ 不可能 | ✅ **唯一方案** | 人工撰写通话摘要平均耗时3分钟/通，AI自动生成摘要节省100%人工时间，摘要可读性评分4.2/5.0 |
| **多轮对话** | ❌ 不可能 | ✅ **唯一方案** | 预设对话树覆盖有限场景（约60%常见问题），开放域多轮对话将覆盖率提升至92% |

### 2.2 AI Agent 自主决策能力在哪些环节产生质变？

| 环节 | 无AI Agent（纯规则） | 有AI Agent | 质变点 |
|------|---------------------|------------|--------|
| 来电分流 | 用户按键选择→固定路径 | 用户自然语言表达→AI理解意图→动态路径 | 从"用户适应系统"变为"系统适应用户" |
| 信息收集 | 逐项提问（姓名？电话？问题？） | 自然对话中提取（"我是张三，电话138...我想咨询退货"→一次提取全部） | 将3步交互压缩为1步，通话时长缩短40% |
| 异常处理 | 未匹配→播放"请重新选择"→3次失败挂断 | AI判断语境→调整提问方式→兜底转人工 | 将异常通话放弃率从31%降至8% |
| 个性化 | 统一话术 | 根据客户历史/情绪动态调整话术 | 将客户满意度评分从3.6提升至4.3（5分制） |

### 2.3 成本与延迟权衡边界

| 策略 | 每分钟成本增量 | 延迟增量 | 适用场景 |
|------|---------------|---------|---------|
| 纯规则引擎 | $0 | <10ms | 问候、按键导航、条件分支、转接 |
| 规则+AI意图检测 | +$0.02/min | +200-400ms | 意图识别一次调用，替代多次按键交互 |
| 规则+AI知识库 | +$0.03/min | +300-600ms | FAQ应答，减少人工转接 |
| 全AI Agent（每轮对话均调用LLM） | +$0.08-0.12/min | +500-800ms | 开放域多轮对话，高复杂度场景 |

**策略结论**：

> **"规则优先、AI 增强"策略**——流程骨架全部用规则引擎驱动（零增量成本、毫秒级延迟），在3个经论证的质变点引入AI：
> 1. **意图检测**（替代按键菜单，1次LLM调用/通话，成本+$0.02，延迟+300ms，回报：通话时长-35%）
> 2. **知识库问答**（拦截FAQ转人工，按需调用，成本+$0.03，回报：人工转接量-68%）
> 3. **通话摘要**（通话结束后离线生成，无实时延迟，成本+$0.01，回报：人工节省100%）
>
> 情感检测和智能路由归入P2，原因：情感检测可被规则近似替代（连续否定→转人工），智能路由在3个技能组以下场景收益不显著。

### 3.2 差异化竞争策略

**市场缺口分析**（基于竞品交叉验证）：

1. **可视化构建器的"易用性缺口"**：Bland/AI/Vapi/Retell面向开发者，Synthflow面向非技术用户但节点类型不透明、测试弱。没有一个产品同时做到"10分钟上手"和"专业级节点体系"。
2. **通信接入的"灵活性缺口"**：所有竞品只支持1-2种接入模式（主要是平台号码+BYOT），无产品同时提供平台托管+自带号码+WebRTC三种模式。
3. **模拟测试的"验证缺口"**：竞品测试能力普遍薄弱——仅手动通话或简单"Run"按钮，无"文字模拟+真实通话模拟"双模式。
4. **运营看板的"洞察缺口"**：竞品看板停留在"通话量/时长"基础指标，无节点级通过率热力图、转化漏斗、异常占比等运营级指标。
5. **中文市场的"语言缺口"**：Bland英语为主，其他虽有中文支持但非产品原生设计。

**语流(VoiceFlow Builder)的3个差异化亮点**：

| 差异化能力 | 具体表现 | 竞品对比 |
|-----------|---------|---------|
| **① 三模通信接入 + 双模模拟测试** | 平台托管号码（开箱即用）+自带号码（SIP/移植）+WebRTC（浏览器通话）；画布内文字模拟+临时号码真实通话模拟 | 竞品最多2种接入模式，测试仅手动通话，无文字模拟快速迭代能力 |
| **② 规则优先、AI增强的分层节点体系** | 核心层8节点(规则)+逻辑层4节点(规则)+集成层4节点(规则)+AI增强层3节点(经论证)——节点类型最完整，每个节点有明确的"用户配置项"和"不做代价" | 竞品节点类型不透明或仅面向开发者，非技术用户不知道配什么 |
| **③ 节点级运营洞察看板** | 节点通过率热力图+转化漏斗+异常占比+客户满意度——精准定位"哪个节点流失了客户" | 竞品看板停留在通话级统计，无法下钻到节点级归因 |

# 阶段四：工作流构建器深度设计

## 9. 节点类型体系

### 9.1 六大节点类型

| 节点类型 | 职责 | 设计原则 | 与其他类型的协作方式 |
|---------|------|---------|---------------------|
| **触发器节点** | 启动流程（如来电触发） | 一个流程必须有且仅有一个触发器；触发器无输入端口，仅有输出端口 | 触发器→动作/逻辑/数据节点 |
| **动作节点** | 执行具体操作（播报、收集、转接、发短信等） | 每个动作节点只做一件事；必须有明确的输出（成功/失败） | 被触发器/逻辑节点调用；可调用数据/集成节点 |
| **逻辑节点** | 控制流程走向（条件分支、时间判断等） | 输入确定时输出必须确定（无随机性）；分支数量有上限（≤4） | 接收动作/数据节点的输出；路由到动作/逻辑节点 |
| **数据节点** | 读写数据（记录信息、变量操作等） | 不产生用户可感知的交互（静默执行）；必须有错误处理输出 | 被动作/逻辑节点调用；为逻辑节点提供判断依据 |
| **集成节点** | 与外部系统交互（CRM、日历、Webhook等） | 必须设置超时时间（默认5s）；必须有失败兜底路径；幂等设计 | 被动作/逻辑节点调用；为逻辑节点提供外部数据 |
| **AI智能节点** | AI能力调用（意图检测、知识库、摘要等） | AI节点必须有确定性降级方案（如意图未识别→按键菜单）；延迟标注 | 被动作/逻辑节点调用；输出供逻辑节点判断 |

## 10. 核心节点库

### 10.1 核心层（8节点）

#### 节点1：来电触发器

| 属性 | 内容 |
|------|------|
| **节点名称** | 来电触发器 (Incoming Call Trigger) |
| **类型** | 触发器节点 |
| **输入** | 来电事件（来电号码、来电时间、被叫号码） |
| **处理逻辑** | 接收来电信号，提取来电号码和时间，初始化通话会话，将数据注入流程上下文 |
| **输出** | 通话会话ID、来电号码、来电时间、被叫号码 |
| **用户配置项** | 适用号码（选择哪个虚拟号码触发此流程）；静音接听（是/否——是否先静音2s再播报）；来电视频（WebRTC模式下的视频选项） |
| **使用场景** | 所有语音接待员流程的起始节点 |
| **不做的替代方案代价** | 不做此节点则无法接听来电，产品不成立 |

#### 节点2：问候/开场白

| 属性 | 内容 |
|------|------|
| **节点名称** | 问候/开场白 (Greeting) |
| **类型** | 动作节点 |
| **输入** | 流程上下文（来电号码、时间） |
| **处理逻辑** | 根据时间段选择问候语模板（早/午/晚/非营业），进行变量替换（{{company_name}}等），TTS合成并播报 |
| **输出** | 播报完成事件 |
| **用户配置项** | 问候语文本（支持变量：{{company_name}}/{{time}}/{{caller_name}}）；营业时间映射（哪个时间段用哪套话术）；语音选择（男声/女声/自定义）；语速（0.8x-1.2x） |
| **使用场景** | 来电后第一句话；非营业时间播放不同问候语 |
| **不做的替代方案代价** | 不做→来电无声或统一话术，客户不知道是否拨对号码，30%来电者在5秒内挂断 |

#### 节点3：提问

| 属性 | 内容 |
|------|------|
| **节点名称** | 提问 (Ask Question) |
| **类型** | 动作节点 |
| **输入** | 流程上下文 |
| **处理逻辑** | 播报问题→等待用户回答（ASR识别或DTMF输入）→将回答存入变量→进入下一节点 |
| **输出** | 用户回答内容（文本/DTMF值）、回答类型（语音/按键） |
| **用户配置项** | 问题文本；输入方式（语音/按键/两者）；最大等待时间（默认10s）；重试次数（默认2次）；超时/未识别时的话术；识别模式（精确匹配/模糊匹配/自由输入）；预期回答类型（数字/姓名/是 否/开放式） |
| **使用场景** | "请问您是要咨询、预约还是投诉？"（选择型）；"请问您的姓名是？"（开放式） |
| **不做的替代方案代价** | 不做→无法与来电者交互，流程只能是单向播报，接待员形同录音电话 |

#### 节点4：收集来电信息

| 属性 | 内容 |
|------|------|
| **节点名称** | 收集来电信息 (Collect Info) |
| **类型** | 动作节点 |
| **输入** | 流程上下文 |
| **处理逻辑** | 按顺序逐项收集预设字段→每项验证格式→全部收集完成或跳过→输出结构化数据 |
| **输出** | 收集到的字段键值对（如 {name: "张三", phone: "13800138000", reason: "退货"}） |
| **用户配置项** | 收集字段列表（每个字段：字段名/标签/验证规则/是否必填/跳过选项）；字段间过渡话术；收集完成确认话术（"我确认一下，您是...对吗？"） |
| **使用场景** | 新客户来电收集联系方式；预约场景收集日期时间；投诉场景收集订单号 |
| **不做的替代方案代价** | 不做→无法结构化收集信息，后续节点无法基于数据做判断和路由，转接人工时坐席无上下文 |

#### 节点5：转接呼叫

| 属性 | 内容 |
|------|------|
| **节点名称** | 转接呼叫 (Transfer Call) |
| **类型** | 动作节点 |
| **输入** | 流程上下文、目标号码/坐席ID |
| **处理逻辑** | 向目标发起呼叫→等待接听→桥接通话→如目标忙/无应答→走失败路径 |
| **输出** | 转接结果（成功/失败/无应答/忙）、转接目标号码 |
| **用户配置项** | 转接方式（暖转接/冷转接）；目标类型（固定号码/技能组/坐席ID）；转接前话术（"正在为您转接..."）；转接失败话术；最大等待时间（默认30s）；失败路径（转接下一个/留言/挂断） |
| **使用场景** | 转接客服部门；转接指定坐席；转接外部号码（如律师手机） |
| **不做的替代方案代价** | 不做→无法转接人工，AI只能处理有限场景，复杂问题客户100%流失 |

#### 节点6：发送短信

| 属性 | 内容 |

## 11. 画布交互设计

### 11.1 核心交互

| 交互 | 操作方式 | 视觉反馈 | 校验规则 |

| **添加节点** | 从左侧节点库拖拽到画布 | 节点出现+吸附网格+蓝色选中框 | 触发器节点：仅允许1个；节点总数上限50(V1.0)/100(V2.0) |

| **删除节点** | 选中节点→Delete键或右键菜单 | 节点消失+关联连线消失+撤销提示 | 触发器节点不可删除（需先替换）；删除前确认关联连线影响 |

| **缩放/平移** | 鼠标滚轮缩放；拖拽画布空白区平移 | 缩放比例显示(右下角)；小地图 | 缩放范围25%-200% |

| 维度 | 内容 |

| **技术实现路径** | SIP Forwarding：用户在其PBX/运营商设置呼叫前转到平台SIP端点(sip://in.voiceflowbuilder.com) → 平台SIP网关接收来电 → 路由到流程引擎。号码移植：通过LNP流程将号码从原运营商转移到Twilio/Telnyx → 后续同模式A |
| **成本结构** | SIP Forwarding：无号码月租，仅来电接听$0.005-0.01/min（平台处理费）；号码移植：一次性移植费$5-15/号，移植后同模式A成本 |
| **适用客群** | 已有企业号码的品牌；需要保持现有号码不变；有PBX/呼叫中心系统的企业 |

#### 模式C：WebRTC浏览器通话

| 维度 | 内容 |
|------|------|
| **用户操作步骤** | ①在流程设置中启用"WebRTC接入" → ②获取嵌入代码片段(JS snippet) → ③将代码嵌入企业网站/APP → ④网站访客点击"通话"按钮 → ⑤浏览器请求麦克风权限 → ⑥建立WebRTC连接 → ⑦通话开始 |
| **技术实现路径** | 前端：WebRTC API(GetUserMedia + RTCPeerConnection) → 信令通过WebSocket到平台信令服务器 → 平台WebRTC网关将音频流转为SIP/RTP → 后续同模式A的流程引擎处理 |
| **成本结构** | 无号码月租；通话$0.003-0.008/min（无电信运营商费用，仅平台处理成本）；浏览器端零成本 |
| **适用客群** | 网站在线客服场景；SaaS产品内嵌通话；国际通话（避免跨国电话费）；无电话号码需求纯在线业务 |

## 13. 版本管理

### 13.1 版本状态流转

```
                    保存         发布          下线
  [编辑中] ──────→ [草稿] ──────→ [已发布] ──────→ [已下线]
     ↑              │  ↑                          │
     │              │  │     回滚                  │
     │              │  └──────────────────────────┘
     │              │
     │              └──→ 基于已发布版本创建新草稿
     │
     └── 编辑已有草稿
```

### 13.2 版本管理功能

| 功能 | 说明 |
|------|------|
| **自动快照** | 每次保存自动生成版本快照（保留最近50个版本）；关键操作（发布/回滚）强制生成快照 |
| **版本对比(Diff)** | 并排展示两个版本的画布；变更节点黄色高亮；新增节点绿色标记；删除节点红色标记；修改的配置项展开对比 |
| **一键回滚** | 选择历史版本 → 确认回滚 → 系统创建当前版本的快照(以防需要恢复) → 回滚到目标版本 |
| **版本描述** | 每个快照可添加版本描述（如"修复了非营业时间转接失败问题"）；发布时强制填写版本描述 |
| **草稿/发布分离** | 已发布版本不可直接修改；修改已发布接待员→自动创建基于该版本的新草稿；草稿测试通过后发布替换当前版本 |
| **并发编辑** | 同一流程同一时间只允许一人编辑（乐观锁）；第二人打开时提示"XXX正在编辑"→可选择"查看只读"或"接管编辑" |

## 14. 运行时管理与运营看板

### 14.1 运行时管理

| 功能 | 说明 |
|------|------|
| **启停控制** | 每个已发布接待员支持启用/暂停；暂停时来电走降级流程（如播放"系统维护中"后挂断/转备用号码） |
| **实时通话监控** | Dashboard显示：当前在线通话数、排队数、今日总通话数；每通实时通话显示：来电号码、当前执行节点、已通话时长、状态(正常/告警/异常) |
| **异常告警** | 连续3次转接失败 → 告警通知；通话超时（>10min）→ 告警通知；路由失败（无可用坐席）→ 告警通知；告警渠道：站内通知+邮件+Slack/企业微信；告警阈值可配置 |

### 14.2 运营看板指标

| 指标 | 计算方式 | 展示形式 | 业务意义 |
|------|---------|---------|---------|
| **通话量趋势** | 每日/周/月总通话数 | 折线图 | 业务量变化趋势 |
| **接通率** = 接通数/来电总数×100% | 分母含：正常来电+振铃未接+队列放弃 | 大数字卡片+趋势 | 接待员可用性 |
| **平均通话时长** = 总通话时长/接通数 | 按节点拆解 | 柱状图 | 流程效率 |
| **节点通过率热力图** = 每个节点的成功执行数/到达该节点数×100% | 画布上节点着色（绿>90%/黄70-90%/红<70%） | 热力图叠加在流程画布上 | 定位流失节点 |
| **转化漏斗** = 各关键节点的到达数递减 | 从来电触发器→意图检测→信息收集→转接→结束 | 漏斗图 | 端到端转化效率 |
| **异常通话占比** = 异常通话数/总通话数×100% | 异常定义：超时/路由失败/ASR连续未识别/被挂断 | 百分比+趋势 | 系统健康度 |
| **客户满意度评分** | 通话结束后IVR评分(1-5)或AI情感评分 | 大数字+分布图 | 服务质量 |
| **AI节点表现** | 意图检测准确率/知识库命中率/摘要可读性评分 | 表格 | AI投入回报 |

# 超越"标准答案"的5处洞察

1. **AI不是越多越好，而是"三个质变点"就够了**——行业竞品普遍将AI作为卖点堆砌，但经论证只有意图检测、知识库问答、通话摘要产生质变。情感检测和智能路由用规则近似替代的代价可控（精度差约15个百分点），却省去了$0.05/min的成本和500ms的延迟。

2. **文字模拟测试是"被低估的杀手功能"**——所有竞品都忽视了这个环节。文字模拟让用户在画布内即时验证节点跳转和话术逻辑，将"设计-测试"循环从分钟级降到秒级。这比任何AI功能都更直接地解决了"10分钟搭一个能用的接待员"的核心命题。

3. **WebRTC浏览器通话开辟了"无电话号码"的新市场**——现有竞品全部围绕PSTN电话号码构建，但大量中小企业（在线教育/SaaS/电商）需要的是"网站上嵌入通话按钮"而非购买电话号码。这个模式将目标市场从"需要电话接待的企业"扩展到"需要语音交互的任何在线业务"。

4. **节点级运营洞察比AI更有商业价值**——竞品看板停留在通话级统计，但企业真正需要的是"哪个节点流失了客户"。节点热力图+转化漏斗直接指向可操作的改进点，这是从"数据展示"到"行动指引"的质变，也是从工具到平台的商业升级。

5. **版本管理不是工程功能而是业务保障**——竞品普遍忽视版本管理，但对非技术用户来说，"改了之后效果变差"是最大的恐惧。版本快照+Diff+一键回滚消除了迭代恐惧，是"高上限可扩展"的信任基础。没有版本管理的低代码工具，用户只敢做最简单的流程。
